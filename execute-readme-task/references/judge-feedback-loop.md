# 外部判题反馈闭环

当测试只能由用户或外部平台执行时，将工作分成“可以独立完成的代码/静态检查”和“必须等待外部证据的动态验证”。不得将建议用户运行的测试写成已通过。

## 在修改前保留基线

记录：

- 当前总分、分组通过数、全部失败提示和提交次数限制；
- 当前已知可通过的业务路径，防止修复时回归；
- 每次修改的文件、根因假设和预期改善的失败簇。

如平台只保留最高分，仍保留本地可回退的每轮差异；不要因为平台保留高分就同时修改多个不相关假设。

## 将反馈转换为假设账本

| 失败簇 | 关联需求/不变量 | 最可能根因 | 最小诊断场景 | 支持/反对证据 | 置信度 | 状态 |
|---|---|---|---|---|---|---|
| 时间边界 | R7/I4 | 使用当前状态而非历史区间 | 转换前发生、转换后上报 | 判题分类 | 高 | 待验证 |

判题提示中的“失败 N 条”可能是交叉归因，不得直接相加。一个失败用例可能同时属于时间、级联、授权和审计。优先寻找能同时解释多个失败簇的共享不变量，而不是按失败数量分别打补丁。

## 按信息增益排序

优先处理：

1. 可以解释多个失败簇的架构或不变量缺口；
2. 不修复就无法可靠测试其他功能的原子性、时间或幂等基础；
3. 能通过一个最小场景证伪的高置信假设；
4. 影响核心难题且与已通过基础用例共享代码路径的问题。

将字段名、错误文案等低信息局部猜测放在后面，除非反馈明确指向契约失败。

## 每轮只验证一类根因

每轮执行：

```text
选择一个高信息假设
-> 找到相关调用链与所有受影响实体
-> 编写最小诊断/回归用例
-> 执行最小一致性修改
-> 请用户运行本地测试按钮
-> 如基础结果不回归，再决定是否消耗提交判分次数
-> 用新证据接受、拒绝或降低假设置信度
```

如新分数下降，先判断是否出现基础回归，再回退本轮最小改动；不要在新的不确定基线上继续叠加修复。

## 向用户请求有效证据

当必须由用户运行时，精确说明：

- 点击哪个按钮或执行哪条命令；
- 需要粘贴哪些完整输出，不要只要“是否通过”；
- 此次测试在区分哪些候选根因；
- 预期哪些已通过场景必须保持不变。

收到反馈后，先复述可观察事实，再更新假设账本。无源码时只能给出根因类别与置信度，不得虚构具体文件或代码行。

## 结束本轮时报告

列出：基线与最新分数、本轮唯一假设、实际改动、本地/外部验证证据、未解释失败簇、当前最高信息的下一个诊断操作。

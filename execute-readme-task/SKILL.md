# 根据 README 规划并执行综合任务

使用低自由度流程。将用户请求视为目标，将 README 视为需求来源，将实际代码视为当前事实。先建立正确的问题模型，再制定详细计划；不要用细节很多但架构错误的计划代替领域建模。

## 先选择任务模式

识别用户当前需要的结果：

- **规划**：输出详细方案，通过计划门禁后停止，不修改代码。
- **实现**：先建模和规划，再逐步修改并验证。
- **诊断**：根据失败证据定位根因；未明示要求时不实施修复。
- **外部判题迭代**：代码可编辑，但测试只能由用户或外部平台运行。

同时检查工具能力：能否搜索文件、编辑、执行命令、运行测试和读取版本差异。对不可用的能力不得伪装已执行。

## 按需读取参考流程

完整读取每个命中条件的参考文件，不要只看标题：

- README 出现状态枚举、版本/修订/代次、历史区间、过期/超时、幂等、并发、原子性、审计、重放、冻结叠加或跨实体级联中任两项，或任务明确要求其中一项时，读取 [复杂状态系统建模](references/stateful-system-modeling.md)。
- 任务修改可观察行为、存在多个业务规则、需要回归验证或有隐藏测试时，读取 [组合测试矩阵](references/test-matrix.md)。
- AI 不能运行终端/测试，依赖“测试”或“提交判分”按钮，或用户提供了分数和失败分类时，读取 [外部判题反馈闭环](references/judge-feedback-loop.md)。

复杂状态型判题通常同时命中三个参考文件。

## 遵守核心规则

1. 先读取、搜索和定位，再建模和规划，最后修改。
2. 将事实、推断、假设和未知项分开记录。
3. 不得虚构未在仓库中找到的文件、符号、字段、命令或依赖。
4. 不得用“修改相关逻辑”“完善异常处理”“增加测试”等空泛表述代替具体机制。
5. 优先复用现有抽象，执行满足需求的最小完整改动，不进行无关重构。
6. 保留与任务无关的用户修改，不覆盖、删除或纳入提交。
7. 每次只实现一个可独立验证的步骤，局部验证通过后再继续。
8. 未执行的检查不得写为通过；没有证据不得声明完成。

## 维护流程状态

在可用时使用计划工具，始终只保留一个 `in_progress` 步骤。

```text
DISCOVER -> CLASSIFY -> CONTRACT -> MODEL -> PLAN
                                   -> EXECUTE -> VERIFY
                                   -> FEEDBACK -> MODEL/PLAN
                                   -> DONE/BLOCKED
```

- `DISCOVER`：读取指令、README、仓库结构和现有测试。
- `CLASSIFY`：确定任务模式、复杂度和需读取的参考文件。
- `CONTRACT`：提取接口、字段、排序、错误、非功能和验收契约。
- `MODEL`：建立架构、调用链、数据流及适用的不变量/状态/事务模型。
- `PLAN`：生成文件与符号级实施蓝图，并通过计划门禁。
- `EXECUTE`：只实现当前原子步骤。
- `VERIFY`：先局部验证，再扩大到受影响范围。
- `FEEDBACK`：根据实际失败更新假设、模型和计划，不盲目打补丁。
- `DONE/BLOCKED`：所有必须需求已有证据，或已明确说明阻塞。

## 完成仓库发现

在编辑前：

1. 完整读取用户请求、README 和适用的仓库指令。
2. 检查仓库状态，记录已有修改和未跟踪文件。
3. 识别语言、框架、入口、依赖、构建方式、配置和测试结构。
4. 搜索 README 中的每个功能名、接口、字段、状态、命令和错误码。
5. 阅读命中定义的调用者、被调用者、测试和配置，不要只看一个文件。
6. 在可执行时运行成本合理的基线测试；不可执行时记录需要用户运行的命令或按钮。

建立仓库证据图：

| 关注点 | 实际位置 | 关键符号/配置 | 作用 | 证据状态 |
|---|---|---|---|---|
| 功能入口 | `path/file` | `Class.method` | 接收请求并调用领域逻辑 | 已读取/待确认 |

如果 README 没有可执行目标，说明缺失并停止，不得自行发明项目。

## 建立契约与需求矩阵

将每个可独立验证的结果拆成一行：

| ID | 可观察结果 | 来源 | 类型 | 优先级 | 验收方法 | 状态 |
|---|---|---|---|---|---|---|
| R1 | 给定输入产生明确输出 | README 章节/用户请求 | 明确/推断/未知 | 必须/应该/可选 | 命令、测试或直接检查 | pending |

必须单独提取：

- 功能行为与失败行为；
- 字段类型、必填性、默认值、可空性、枚举和数值边界；
- 唯一性、排序、去重和过滤规则；
- 兼容性、禁止事项、非功能约束和验收方式。

将 README/用户明示内容标为“明确”，代码结论标为“推断”，缺少决策的内容标为“未知”。未知项如果会改变公开接口、持久数据、安全、成本、主要产品行为或导致破坏性操作，请求用户决策；否则采用最小可逆假设并显式记录。

## 建立实现模型

在规划前引用实际文件和符号回答：

1. 输入如何经过入口、校验、核心服务、存储/外部边界到达输出？
2. 当前行为与每个需求 ID 相比缺少哪个分支、数据、状态转换或错误处理？
3. 需修改的定义被谁调用，它又调用谁？
4. 接口、类型、数据、状态、文件格式和外部消费者中哪些必须保持不变？
5. 现有测试覆盖什么，哪些正常、边界、失败和组合路径尚未覆盖？

对跨模块流程绘制简短文本图。对复杂状态系统，不得在完成适用的不变量、状态转换、级联、时间/版本和事务模型之前开始按接口实现。

## 生成详细改动蓝图

每个改动单元必须包含：

| 字段 | 必须写出的内容 |
|---|---|
| 覆盖契约 | 需求 ID，以及适用的不变量 ID |
| 当前证据 | 现有行为所在文件、符号和关键分支 |
| 改动位置 | 精确文件与类/函数/方法/配置/测试符号 |
| 接口与数据 | 签名、类型、字段、返回值、错误语义和数据流变化 |
| 实现机制 | 按执行顺序写出判断、算法、状态转换和调用 |
| 边界与兼容 | 非法输入、极值、部分失败、超时、重试、并发以及保持不变的行为 |
| 测试设计 | 用例名、前置状态、具体输入、预期输出/副作用、覆盖的契约 |
| 验收与风险 | 精确命令/外部操作、完成标准、回归观测点和最小回退单元 |

简单任务也要填写所有字段；不适用时写明原因，不要删除字段来回避思考。

## 拆分原子执行步骤

按依赖排序：公共契约/事务基础 -> 数据与历史模型 -> 集中领域转换 -> 调用者/接口 -> 失败与组合路径 -> 查询视图/文档 -> 广泛验收。

每个步骤写出：

- **目标和覆盖**：可观察结果、需求 ID 和不变量 ID。
- **前置依赖**：必须先完成的步骤、环境或数据。
- **修改文件与符号**：精确到文件及类、函数、方法、配置或测试用例。
- **实现顺序**：写出校验、计算、数据变换、状态更新、级联和返回的先后关系。
- **保持不变**：列出不应被改变的公开行为和内部不变量。
- **测试用例**：写出测试名、准备数据/模拟、输入、预期输出、副作用和失败时的不变性。
- **验证与完成标准**：实际命令或外部测试操作，以及必须出现的精确结果。
- **回归观测点**：错误实现最可能破坏什么，如何发现。

拆分包含多个主要目标、无法独立验证、混入无关重构或横跨多个高风险边界的步骤。

## 执行计划门禁

在实现前逐项检查：

- [ ] 每个必须需求都被步骤和具体测试覆盖。
- [ ] 每个步骤都引用已读取的实际文件和符号。
- [ ] 正常、边界、失败和兼容路径都已说明。
- [ ] 调用者、被调用者、数据流和影响面均已确认或显式标记待查。
- [ ] 命中参考文件要求的不变量、状态、级联、时间、事务或测试产物均已完成。
- [ ] 每个验证都有具体输入、预期输出/副作用和可执行方式。
- [ ] 步骤依赖无循环，高风险改动有回归检查和最小回退单元。
- [ ] 用户已有改动与本次修改边界已分开。

任何一项未满足时，继续搜索、建模或细化计划，不得开始实现。

## 逐步实现和验证

对当前步骤：

1. 重新读取对应契约、模型、蓝图和目标符号。
2. 如当前代码与计划冲突，先更新模型和计划，不得继续猜测。
3. 只修改当前步骤所需的文件与符号。
4. 在行为变化时添加针对性测试，先覆盖最小可证明场景。
5. 检查差异，移除偶然改动和不必要的复杂度。
6. 执行最小验证，再执行受影响模块、静态/类型检查、构建和广泛回归。
7. 如无法本地执行，向用户提供精确测试操作，等待实际结果，不得自行假定通过。
8. 只在预期断言、输出、副作用和不变量都符合时标记完成。

验证失败时，保留精确证据，将失败分为实现、契约、模型、测试预期、环境、依赖、权限或需求歧义。一次只验证一个根因假设。同一症状连续修正两次仍失败时，停止打补丁，回到 `MODEL`。

## 执行完成门禁

只有同时满足以下条件才进入 `DONE`：

- 每个必须需求均为 `pass`、有理由的 `not applicable` 或有证据的 `blocked`。
- 每个 `pass` 均引用实现位置和实际验证结果。
- 正常、边界、失败和适用的组合路径已验证，或明确列为限制。
- 所有已知失败均已报告，未执行项未被冒充为通过。
- 最终差异不包含无关用户文件或意外生成物。
- 文档、接口、配置、存储状态和查询视图一致。

## 输出结果

规划模式输出：任务范围、需求矩阵、仓库证据图、调用链/数据流、适用的领域模型产物、详细改动蓝图、原子步骤、测试矩阵、风险和未知项。

实现模式最终输出：

1. **结果**：完成、部分完成或受阻。
2. **需求验收**：逐个 ID 列出状态、实现文件/符号与验证证据。
3. **验证结果**：只列出实际执行过的命令或用户反馈。
4. **假设与限制**：只列实质影响结果的假设、受阻项和未验证项。
